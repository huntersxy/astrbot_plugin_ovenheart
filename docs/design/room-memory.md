# 0.67 通用记忆的原版检索通道

在已有 A_memorix 人物事实通道上继续移植15个原模块，现共37个上游模块。来源仍为 MaiBot `5c7637e6913c84d1c3d5e742fa9e95a7e70d3501`。双路检索、BM25、分数校准、后验图门控、关系召回、PageRank、图存储、Faiss向量存储和关系写入服务沿用原文算法；只调整宿主日志导入。来源清单及原/移植哈希见 `vendor/maibot/amemorix/source_manifest.json`。

## 本地运行链

- `native_memory_enabled` 默认开启，并遵守 `memory_enabled`、宿主访问、当前会话/人格及底稿开关。写入还遵守学习开关与成员/群聊学习排除。
- `remember_memory` 只接受本轮真实消息的原文引用。先完成整份结构校验，再从仍获准访问的原事件解析作者、消息ID和时间；不能将自己的回复或窗口外引用当成人类证据。
- 元数据位于 `amemorix/rooms/<native-scope>/metadata/metadata.db`。不同会话/人格的段落、图和索引分目录保存，习惯共享开关不扩大记忆访问范围。
- 原 `MetadataStore` 是主数据源，原 `RelationWriteService` 写入关系与图。参与者字段只表示来源，不等于每条事实属于所有参与者。重复段落保留去重后的首条和近期原文证据，最多64条。
- 原 `DualPathRetriever` 同时使用段落、关系、BM25、图及PageRank。配置 AstrBot 嵌入提供商后，原 `VectorStore` 使用独立段落池与图池，图池采用原 `entity:` / `relation:` 类型ID。
- 嵌入运输由 AstrBot SDK 提供，模型指纹和真实维度决定索引空间。模型改变时保留旧索引，使用原元数据与回填队列建立新空间，避免混用向量。原索引加载后必须调用 `warmup_index()`，否则小库 fallback 尚未回放，会出现“文件在但查不到”的情况。
- 嵌入异常不回滚已存元数据；本轮使用原稀疏/图通道。准备与回填阶段各有短网络等待，外层仍有检索预算。取消会传到运行中的原检索任务及原生嵌入请求；同步初始化和磁盘工作不等于整体回复耗时。
- 同一会话的初始化和实际存储修改串行；整理等待模型期间，前台查询/保存借用同一个持续后台循环，后台恢复提交前先等待已开始的前台操作完成。模型网络请求回到宿主事件循环执行。最多保留64个已加载会话，LRU释放和关闭会等待正在初始化、执行及登记的读操作完成。
- Planner 的查询工具和回复器读取同一份通用记忆。回复注入保持临时内容，包含有界原文来源，不将内部档案或检索片段写成聊天历史。人物账本中已经确认的更正优先于通用旧回忆。

依赖扩展为上游使用的 `faiss-cpu>=1.11.0`、`numpy>=2.2.6`、`scipy>=1.7.0` 与 `jieba>=0.42.1`。这意味着生产部署前需要更新依赖并执行真实SDK安装包预检；本阶段未部署。

## 已验证及仍待完成

使用实际SQLite、图存储和Faiss测试原文来源、作用域隔离、双向量池、非词面查询、重开回放、模型空间切换、嵌入失败/取消、并发首次写入及重复来源保留；只有外部嵌入模型返回受控合成向量。隔离AstrBot完整内核覆盖通用记忆写入/查询、人物记忆写入/查询、两次原生回复、结果回流和stop，内部记忆没有落入宿主聊天历史。

后续阶段已经把通用存储所有权、读写和摘要/情景入口交给实际 SDK 内核，接管与剩余后台桥接见 [native-memory-kernel.md](native-memory-kernel.md)。自动群聊摘要、情景生成/召回见 [memory-consolidation.md](memory-consolidation.md)。独立中期记忆、图片记忆、通用记忆纠错/遗忘与生命周期维护、人物和通用检索进一步贯通、旧LivingMemory数据导入以及完整模型用量聚合仍需继续。LivingMemory及其旧数据保持原样，现阶段提供并行旧回忆参考。实际模型下的语义归纳和自然回复效果仍未完成对照验收。

本阶段验证：778项完整Python回归、31项前端测试、Ruff、JS语法、37个来源文件哈希、关键算法主体对照及真实发布包独立导入检查通过。使用本机AstrBot 4.29.1；没有发送QQ消息，没有将受控模型/嵌入响应当成真实自然表达或语义质量验收。
