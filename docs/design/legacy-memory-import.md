# LivingMemory 旧记忆迁入

迁入通过烤箱之心原生 Panel 的当前会话/人格入口执行：`legacy_preview` 只读预览，`legacy_import` 启动后台任务，进度随设置页更新。仅接受已存在的作用域及近期真实来源，不接受任意数据库路径、文件内容或模型指定的目标会话。旧 LivingMemory 不是安装依赖，未启用时原生记忆仍可独立运行。

沿用旧插件的访问规则及实际存储作用域，只选择目标人格的旧全局/当前会话记录。用户隔离的旧记忆仅允许迁入该用户自己的原生私聊，不能直接变成群共享记忆；旧白名单只允许部分成员时，也不扩大到整群。配置或来源实例变化会停止任务，保留已提交内容并允许重复执行。

正式迁入前，以 SQLite 在线备份 API 建立完整一致性快照，位于自有数据目录 `amemorix/livingmemory_imports`。源连接使用只读 URI，没有修改旧库、旧配置、第三方源码或版本。快照保留全部原文、消息来源、原子及派生图，故障后可以继续查阅。预览不创建快照、不初始化原生内核、不调用模型。

依据旧库实际生命周期读取当前有效内容：有原子记录或原子类型标记时，只导入 `active` 且尚未过期的原子，不再次灌入仍含旧事实的父正文；没有原子时迁入有效原文及其仍有效的直接图关系。原子对应的实体保留，其父文档中无法与有效原子准确对应的派生图仅保留在完整快照中。原子的过期时间沿用到原 SDK；同一内容的多个有效旧来源在自有导入记录中保留映射，不缩短已有原生内容寿命。

迁入通过同一原 SDK `ingest_text` 写入当前会话/人格的段落及关系。自有映射记录按旧库命名空间、原记忆和原子编号去重；相同正文复用原有记录，原生侧的更正/遗忘保持权威，重复迁入不复活已删除内容。已有旧编号的正文改变时报告冲突，不静默覆盖。原生记忆没有旧消息伪造的“当前证据”；保留有明确 `livingmemory:` 前缀的旧本地编号与有限来源摘录，完整来源留在快照。不把旧模型摘要自动登记为当前作者新自述或人物稳定事实。

逐条提交后释放原生工作队列，聊天请求可在条目之间继续使用同一内核。整个匹配批次成功且权限仍有效时，持久化已迁入标记：本桥停止重复召回，已绑定的旧 LLM 召回/反思钩子跳过该作用域。若钩子尚未绑定，进度明确提示数据已迁入但运行切换待核验；不把写库成功等同于线上钩子验收。其它会话和人格、旧插件原始数据与后台功能保持原样。冲突或中途失败不会创建新的整批切换标记。

2026-10-26只读生产核对：旧插件2.7.1，425条记忆均属于`kxcz`，397条为旧全局范围，其余为历史会话范围；原子中1757条标为active、58条expired、31条forgotten。active还须经过当前过期时间筛选，不能把这个计数直接当成可迁入数。对约92MB的一致性快照执行了当前读取函数的实际代码：397条全局记忆形成1772条有效内容单元，排除95条失效原子。该数量包含无原子旧文档回退，不能等同于active原子数。临时快照已清理，生产记忆没有迁移或改写。

两个定向场景使用旧插件源码中的实际 DDL、真实 SQLite 快照、原访问策略及原 SDK：有效原子替代旧父正文、失效排除、会话/人格匹配、来源与完整快照、零生成调用、切换标记重开；重复迁入、原生遗忘不复活及成员白名单不扩权。只有旧插件实例和外部环境入口受控，未跑全量回归；线上写入及真实钩子仍待随完整版本验收。


线上0.67.0诊断定位到两个已启用的LLM钩子残留旧烤箱之心 routed 函数，导致新桥无法识别实际原生所有者。适配只拆解本模块同名包装，并逐层核对 _owner 与当前官方实例相同、底层回调确实绑定该实例，再由新桥接管；不接管未知包装或旧第三方实例。定向验证覆盖原回调只调用一次、旧桥退出不破坏新桥、卸载恢复原回调及拒绝过期所有者。


## 缺少近期消息时排队

启动迁入时若当前会话尚无近期真实来源，只将管理员请求存入自有SQLite的legacy_import_queue，显示waiting_source；不创建快照、不调用模型、不读取旧库。插件重载后恢复等待。该作用域下一条实际获准消息完成采集后，后台用该原生事件重新核对当前人格、学习权限、旧插件会话开关/白名单/实例和来源，再执行正常备份与迁入。无法通过检查时停止并明确显示原因，不能把保存过的旧请求当成权限。

工坊可取消等待或运行中的任务，已经成功写入的原生内容与原库保留。正常结束、明确取消或错误会移除队列项；插件关闭造成的中断保留请求，重载后在下一条真实消息重新校验，按已有导入映射跳过已完成内容。预览保持只读，有排队请求时先取消再预览。没有发送任何QQ验收消息。

定向验证：无真实来源时排队不产生备份；重建迁入服务后能从SQLite恢复；取消会清空队列；重新排队后，真实SDK消息采集触发同一有效原子导入，并在完成后清除队列。
