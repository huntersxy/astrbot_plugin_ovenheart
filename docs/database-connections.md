# 数据库连接评估

2026-10-28，根据当前调用路径和本地合成数据对比，采用“主库单写长连接、独立只读短连接、记忆库按既有驻留上限复用”的方案。

## 连接策略

| 路径 | 原行为 | 调整与理由 |
| --- | --- | --- |
| `Store.call`：采集、上下文、配置、运行记录 | 每次在线程池中连接、提交/回滚、关闭 | 单个专用线程持有一个连接，复用 SQLite 页缓存和语句缓存；操作仍串行、分别提交/回滚。 |
| `Store.read`：回复准备与 Panel 查询 | 独立只读连接和显式读事务，读取后关闭 | 保留。读请求绕过写队列，每次查询有一致快照，完成后及时释放读事务。 |
| 人物与通用/图片记忆内核 | SDK 已按线程复用连接，会话内核受驻留上限约束 | 保留。长期保留所有会话内核会增加内存和连接占用，不应仅因关闭日志较多就取消回收。 |
| 跨会话检索后的反馈入队 | 每个命中会话额外创建 `MetadataStore`，检查结构后写入、关闭 | 已驻留会话走现有 `queue_feedback` 操作，复用内核连接和调度；冷会话仍临时连接，避免为了入队重新加载整套内核。 |
| 主动复核的素材检查 | `with sqlite3.connect(...)`，连接依赖回收释放 | 改用 `contextlib.closing`，成功或异常退出都显式关闭。临时反馈连接初始化也纳入 `finally` 清理。 |

## 为什么只复用写连接

Python 的 SQLite 语句缓存属于连接，每次重新连接都需要重新积累。WAL 的最后一个连接关闭时还会执行 checkpoint 并清理辅助文件；主库频繁写入后立即关闭，会反复支付这些成本。保留一个写连接能减少连接建立、SQL 准备和 WAL 收尾工作。

长连接只保留连接资源，每次操作仍结束事务，空闲期间不保留写事务。创建、使用与关闭都在同一个工作线程执行，保留 SQLite 默认的线程检查。调用被取消时等待已提交给线程的工作结束，再释放操作锁；重复取消也不会让关闭越过正在执行的事务。

读取继续使用独立的只读连接，避免查询排在写入后面，也避免共享连接上的事务相互影响。查询结束即关闭，防止把读快照保留到下一次请求。暂不增加读连接池，后续只有实际查询剖析证明有必要时再评估。

保留原有 WAL、同步级别、每次操作的提交粒度、10 秒写入锁等待、2 秒只读锁等待和自动 checkpoint 设置。数据库结构、依赖与现有数据无需迁移。

插件卸载先停止业务任务、刷新用量并关闭记忆内核，再关闭主库连接和专用线程。关闭后的 `Store` 拒绝新操作；重载创建新实例。运行中可能保留 `-wal` / `-shm` 文件，备份继续使用 SQLite 一致性快照，不能只复制正在使用的主库文件。

## 本地验证

比较基线为提交 `d2a6cc8`。环境为 Windows、Python 3.12.10、SQLite 3.49.1；使用临时数据库和合成消息，不读取生产数据。

两种实现使用相同表结构和参数，各执行 5 轮；交替运行先后顺序，每轮预热后分别执行 300 次消息采集、上下文追加和会话资料读取。下表是各轮平均单次耗时的中位数，包含异步调度与 SQLite 操作。

| 操作 | 调整前 | 调整后 | 耗时下降 |
| --- | ---: | ---: | ---: |
| 消息采集 `capture` | 3.4809 ms | 0.6087 ms | 82.5% |
| 上下文追加 `chat_context` | 3.9550 ms | 0.8491 ms | 78.5% |
| 会话资料读取 `scope_profile` | 0.9483 ms | 0.6204 ms | 34.6% |

上述混合操作连同初始化、预热，共建立连接 4520 → 1510 次。写连接从每次操作创建变为每个实例创建一次；读取仍是短连接，但写连接存续期间无需反复重建 WAL 工作环境。

8 项定向检查通过：写连接复用与线程归属、异常回滚后继续写入、未提交写入期间并发读取、读快照一致性与释放、重复取消和关闭等待、未打开连接时关闭与重载、复核连接成功/异常释放、反馈入队的热/冷会话分流。各轮数据库 `integrity_check` 均返回 `ok`。这些结果只说明本机测试场景，不能直接换算为生产端到端聊天提速。

另用真实记忆库验证热、冷反馈入队具有相同标识，重复入队只有一条任务，来源会话保持一致。全库 Ruff 检查和改动 Python 文件编译检查通过；未做生产消息验收。
