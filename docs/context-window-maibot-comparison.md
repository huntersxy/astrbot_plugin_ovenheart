# 结构化上下文窗口与 MaiBot 的比较

研究日期：2026-10-30。

比较基准：OvenHeart `66b90ec8e216a387e634b1c779d280e7220f7928`，本机 MaiBot `5c7637e6913c84d1c3d5e742fa9e95a7e70d3501`。MaiBot 参考仓库为工作区相邻的 `MaiBot/`。结论针对这些源码快照，不表示上游最新版本，也不表示模型实际回复效果已经验收。

本次以 OvenHeart 的 `structured` 群聊路径与 MaiBot 的 Maisaka 普通群聊路径为主。数值使用当前 OvenHeart 默认窗口和 MaiBot 源码默认配置；MaiBot 的实际运行配置可能不同。Focus 聚合模式有独立的上下文压缩路径，不能套用普通模式的全部数值。

## 核心区别

OvenHeart 在 AstrBot 的原生对话历史和请求管线上，补充一份有界的结构化群聊窗口、明确的回复目标和相关记忆。MaiBot 自己维护运行时历史，再从这份历史构造 Planner 与 replyer 的不同输入。

两者都有消息身份、回复目标、机器人自己的发言、媒体占位和旧记忆。主要区别在于历史由谁维护、如何裁切，以及规划与回复分别保留了哪些信息。

| 比较项 | OvenHeart structured | MaiBot Maisaka 普通群聊 |
| --- | --- | --- |
| 历史归属 | AstrBot 原生历史继续存在，OvenHeart 另存有界的群聊账本并补充请求 | 自己维护 `_chat_history`，其中包含真实收发消息及内部规划、工具和参考信息 |
| 收集单位 | 消息记录包含成员 ID、消息 ID、时间、正文、引用、提及、媒体、自身标记 | `SessionBackedMessage` 保留原始 `SessionMessage`，其他类型表示模型输出、工具结果或参考 |
| 规划输入 | 最近最多 40 条，完整记录序列化预算 24000 字符 | 群聊基础窗口默认 40，选择器使用 2 倍缓存窗口，并维护完整工具轮次 |
| 回复历史 | 默认附加最近最多 12 条、12000 字符的紧凑窗口，目标和 focus 另外保留；原生历史另算 | reply 工具复制共享历史，replyer 过滤后保留真实收发的 IM 消息；没有同样的独立 12 条附加窗口 |
| 角色表达 | 群聊窗口以结构化数据放入本轮临时 user 内容；原生 user/assistant 历史继续保留 | replyer 将真实用户消息转为 user 内容，将实际发送的 `guided_reply` 转为 assistant 内容 |
| 回复对象 | Planner 使用本轮消息序号，宿主校验并冻结目标；直接回复也构造明确目标 | Planner 的 reply 工具选择 `msg_id`，定位原始消息后交给 replyer |
| 相关前文 | 额外保留目标、该成员 10 分钟内最近 4 条前文、机器人最近 3 条自身发言及引用 | replyer 使用共享历史中过滤出的真实聊天，并接收明确目标与 `reply_reference` |
| 媒体 | 附加窗口主要提供描述、状态及图片引用；当前原请求的媒体由 AstrBot 保留，历史图片可通过工具查询 | 保留原消息组件，支持将窗口内图片作为实际多模态内容输入，也支持文字占位、描述刷新与图片数量限制 |
| 淘汰和回想 | 账本每范围最多 160 条；规划和回复各自截取。中期记忆观察滑出规划快照的旧记录，后台摘要、按需召回 | 普通历史超过基础窗口 2 倍后，在轮末裁至基础窗口附近；工具轮次按整体处理，裁下的历史可触发聊天回想和学习 |
| 重启与清理 | 持久账本按会话、人格及原生对话 ID/epoch 管理；新范围可从宿主消息库补种 | 启动从消息库恢复基础窗口一半的近期记录，尊重 `/clear` 边界，并附加离线间隔说明 |

## 数值的实际含义

OvenHeart 存在三个不同层级：

1. **账本**：`Store.chat_context()` 每个范围最多保留 160 条，最多保留 128 个范围的账本。
2. **规划快照**：`ConversationContext.snapshot()` 从账本截取最近最多 40 条，受 24000 字符预算限制。该预算按完整记录的 JSON 计算，包含元数据。
3. **回复附加窗口**：`reply_messages()` 默认从规划快照取最近最多 12 条，按紧凑模型字段计算 12000 字符预算。

当前目标、`reply_focus`、人物画像、召回记忆、人格、原生历史、工具定义以及自定义模板另行计入请求。12000 字符不是整个请求上限，也不是 token 上限。`payload_view()` 会在附加数据内部引用已经出现过的相同 focus 摘录，但没有对整个 AstrBot 原生历史执行跨层去重。

MaiBot 普通群聊的基础默认值也是 40，但统计的是 `count_in_context` 条目，包含适用的内部消息或模型输出，不等同于 40 条群友发言。上下文选择器使用 `CONTEXT_SELECTION_CACHE_STABILITY_RATIO = 2.0`；历史超过 80 个可计数条目后，轮末处理会尝试裁到 40。参考条目及完整工具轮次可能使最终输入超出基础数量。replyer 再过滤真实 IM 消息，因此这些数字也不能直接当成 replyer 的真实聊天条数。

这两套机制都不能只用一个“窗口条数”代表最终模型输入量。

## 离线样例：较早目标保住了，附近对话未必保住

使用 OvenHeart 的真实 `snapshot()`、`reply_messages()`、`focus()` 和 `payload_view()`，构造 40 条不超预算的结构化记录，选择第 10 条为目标。第 11、21、31 条为机器人已发送的消息，其余为不同成员的发言。

结果：

- Planner 快照包含 40 条。
- 回复附加窗口包含第 29～40 条。
- 第 10 条作为 `reply_message` 单独保留。
- 第 11、21、31 条通过自身发言 focus 保留。
- 目标附近其他成员的第 9、12 条不在这份附加上下文中。
- 此样例窗口为 2642 字符，整个回复数据为 3454 字符；两者预算口径不同。
- 将附加窗口条数或字符预算设为 0，仍保留明确目标与 focus。
- 原始 40 条记录没有被上述模型视图函数修改。

这证明了截取行为，并不证明模型一定会答错。原生对话历史、显式引用或 Planner 的 `reply_reference` 仍可能提供缺少的信息。需要检查完整最终请求，才能确定某一轮是否真的缺失。

例如，A 的问题依赖 B 在前一句给出的约束，而目标之后已经出现大量新闲聊：规划器可能见过 B 的约束，回复器的附加窗口却只保留目标和较新闲聊。若该约束未进入原生历史、引用或规划说明，最终回复就可能失去依据。这是当前窗口优先级值得优先研究的具体场景。

## 当前设计值得保留的部分

- 回复目标独立于附加窗口，不因把窗口调小而直接丢失。
- 同成员前文与机器人自身发言分开组织，便于核对“你刚才说的”和后续更正。
- 账本按实际会话和人格管理，不依赖昵称判断身份；共享习惯设置不等于合并群聊账本。
- 图片描述未完成时保留占位与消息身份，描述完成后更新原记录。
- 新对话、重置及过期规划都有会话边界检查。
- OvenHeart 自身发言记录和 Planner 回执使用实际成功发送的段落；AstrBot 原生历史仍按宿主机制保存，两者的发送记录口径需要分别观察。

## 优先研究的问题

1. **规划与回复之间的信息交接。** 比较“最近窗口”与“围绕实际目标选择相关前后文”的覆盖情况，重点观察引用链、其他成员补充的条件和目标之后的新闲聊。保留目标、自身发言和身份边界。
2. **整个最终请求的重复和预算。** 记录原生历史、附加群聊窗口、目标/focus、人格、记忆、工具定义分别占用多少字符及实际 token。先查重复来自哪里，再决定是否调整数量。OvenHeart 的窗口内去重与 bili 的上游压缩应分别评估。
3. **媒体信息是否足以完成任务。** 区分当前图片、历史描述、可检索原图和仍在识别的图片；使用需要视觉细节的实际问题比较两种输入。仅凭“有图片描述”无法证明具备原图的全部信息。
4. **跨轮和长时间间隔。** 比较重启、清空、新对话、长时间静默及中期回想的行为。MaiBot 有专门的离线时间说明；OvenHeart 现有时间戳、会话边界和恢复标记仍需结合真实请求检查。

第一优先项是目标附近的有效语境能否从规划传到回复；目前证据不支持直接把 12 条改成 40 条，也不支持断言 MaiBot 的模型回复一定更自然或更准确。
